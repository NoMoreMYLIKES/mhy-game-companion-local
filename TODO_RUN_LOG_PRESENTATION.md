# TODO: Separate Companion Summaries from Executor Output

Date: 2026-10-24

Status: Follow-up proposal. A narrow BetterGI presentation change was implemented locally during this discussion; the shared solution below has not been implemented. This document records the discussion and does not imply that those local code changes are included in this documentation-only commit.

## Goal

On the Runs page, clearly separate information generated by Game Companion (the hub) from information returned by BetterGI or OneDragon. Both games must use the same presentation model. Users should be able to distinguish the hub's assessment from the executor's own words without interpreting their placement or color.

Use neutral introductory copy for executor output. A log level such as `[ERR]` or `[ERROR]` must remain visible inside the log block, but should not automatically become a hub-authored warning that the task failed. Equally, an exited process must not be described as a successfully completed task without supporting evidence.

## What happened in this discussion

The initial report concerned the Chinese message `BetterGI 已执行完，但日志中有错误：` followed by a timestamped BetterGI log line. The requested presentation had two parts: a neutral fixed message and a theme-compatible code block containing the executor output.

The local implementation changed the message to `BetterGI 执行完毕，日志如下：` (English: `BetterGI finished. Log output:`), added a themed `<pre><code>` block, and recognized old and new Chinese/English prefixes so existing BetterGI records could use the same display. The block uses a monospace font, theme tokens, wrapping, a height limit, keyboard focus, and HTML escaping. Default and Proxy/ZZZ theme rules were added.

That change was too narrow. `runNote()` only handles a Genshin note with a recognized BetterGI prefix. It does not handle OneDragon output, and it does not cover every BetterGI error path either. The user then supplied this OneDragon example, which still appeared as ordinary error paragraphs:

```text
[18:00:33.144] [operation.py 702] [ERROR]: 指令[ 进入游戏 ] 执行失败 返回状态 异常
[18:00:33.145] [operation.py 702] [ERROR]: 指令[ 打开并登录游戏 ] 执行失败 返回状态 异常
[18:00:33.145] [operation.py 702] [ERROR]: 指令[ 一条龙 ] 执行失败 返回状态 异常
```

The same record also showed a task/goal label and the hub-generated note that the live Battery Charge adapter was not detected. These are different kinds of content and should not be presented as a single stream of executor output.

## Verified cause and diagnostic limits

`server/tools.py::parse_bgi()` and `parse_zzz()` have different receipt formats. For the original BetterGI completion case, `server/runner.py::_receipt()` builds a note from a fixed prefix plus selected log entries. For an unconfirmed/failed OneDragon run, it appends selected raw log lines to the game's `errors` array. `web/app.js::runGame()` renders that array directly as error paragraphs, bypassing the BetterGI-specific note renderer.

The deeper issue is that `errors` and `notes` describe severity while mixing content sources. They contain both hub-authored messages and executor output. The requested UI separation is by source, so changing one message prefix cannot solve it. Different executor parsers are necessary; different presentation rules are not.

Running the supplied three lines through `parse_zzz()` confirmed three raw error entries, a failed OneDragon outcome, and failed commands for entering the game, opening/logging in, and OneDragon. Their timestamps and nesting suggest propagation of one underlying failure, but these lines do not establish its original cause. Earlier exception details or a traceback would be needed.

The Battery Charge adapter note is generated separately by the hub when a farming item exists and `zzz_patch_ok()` cannot confirm the expected source markers. It describes a farming capability limitation, not evidence of the cause of the login failure. Keep it outside the executor log block. Keep the task and cultivation target in the summary area.

## Proposed presentation contract

| Area | Content and responsibility |
| --- | --- |
| Companion summary | Game, task, cultivation target, timing, confirmed completion amount, and the existing run outcome. |
| Companion notices | Configuration, timeout, stop, receipt availability, and other hub-authored explanations. |
| Executor output | Source label (`BetterGI` or `OneDragon`) and log text in a shared, theme-aware code block. |

Use a neutral heading such as `Executor log excerpt`, with the source shown separately. Where a sentence is appropriate, `This run has ended. Executor output follows:` describes lifecycle without promising success. Localize visible labels through the normal catalog. Keep outcome badges separate from the log heading; preserve accurate failure information in both the badge and the original log text.

Both current parsers select recent entries and truncate individual messages. The current UI therefore has excerpts, not guaranteed complete raw output. Preserve the text actually stored and label it accordingly. Complete per-run output capture is a separate enhancement; a presentation change cannot recover content already discarded.

## Implementation TODO

- [ ] Define a versioned record/view contract with separate hub summary/notices, executor identity, executor result evidence, and log excerpts. Record truncation/completeness explicitly. Choose final field names before changing the producers; do not embed localized headings in new log fields.
- [ ] Keep BetterGI and OneDragon parsing specific to their native formats, but map their results into the shared contract. Preserve the existing run-status and completion-count rules in this first change; do not equate process exit with success or a log-level token with task failure.
- [ ] Update receipt generation so new records no longer mix executor text into hub-facing `errors` or `notes`. Audit downstream consumers of these fields, including summaries and notifications, before changing their contract. Keep meaningful configuration and orchestration failures available to those consumers.
- [ ] Replace the BetterGI-only renderer with shared summary, notice, and executor-log rendering for both games. Select the display by explicit source/type fields, not translated message prefixes. Show each selected log entry once, without repeating it in both the summary and the code block.
- [ ] Add a read-time adapter for old records. Prefer existing structured parsed-log fields when available; use narrowly scoped legacy recognition only in this adapter. Preserve stored records and original text. If provenance is ambiguous, retain a clearly identified legacy detail instead of silently discarding or falsely classifying it.
- [ ] Reuse existing theme tokens for the default and Proxy/ZZZ themes in light and dark modes. Keep log typography monospace, preserve line breaks, wrap long lines, limit height with internal scrolling, and provide visible keyboard focus. Do not color the entire log block as a hub failure solely because it contains an error-level entry.
- [ ] Add a copy action that copies only the displayed log text, with accessible labeling and feedback. Keep executor output escaped as text; never interpret log content as HTML.
- [ ] Remove the previous BetterGI-specific presentation path once legacy records are handled by the adapter. Retain compatibility for both Chinese and English saved messages and localize the new shared labels.
- [ ] Review outcome wording separately if needed. Candidate labels discussed were Running, Completed, Incomplete, Stopped, and Result unconfirmed; these are proposals, not permission to silently remap existing statuses during this UI change.
- [ ] Consider full per-run log capture later, with explicit retention and size limits. Only label output as complete when the storage pipeline actually guarantees it.
